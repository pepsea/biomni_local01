# 42. 「呼び出しが失敗した」は「データが無い」ではない

## 症状

```
調査の結果、FGFR1 が骨粗鬆症治療薬としての妥当性を示すメカニズムに関する
明確な根拠は得られなかった。UniProt への複数回の API アクセスが失敗しており、
FGFR1 の機能情報取得に必要なデータが入手できなかった。
```

読むと「UniProt に FGFR1 の情報が無い」あるいは「UniProt が落ちていた」と
受け取れます。**どちらも違います。**

実際に起きていたのはこれです。

```
Error: unhashable type: 'slice'        ← 辞書を r[:800] した
Error: 'results'                       ← 無いキーを引いた
Error: expected an indented block      ← if の次の行が下がっていない
```

**全部こちらの書いたコードの誤りです。** UniProt は正常で、FGFR1 の
エントリも当然あります。にもかかわらず、結論は「根拠が得られなかった」に
なりました。研究の道具としては、これが最も危険な壊れ方です。
**無いことの証明として読まれてしまいます。**

## 直し方

### 1. 失敗の中身を分けて数える

観測を「外部の失敗」と「こちらのコードの誤り」に分けます。

```python
CLIENT_ERROR_MARKS = (
    "unhashable type", "indices must be integers", "is not defined",
    "unexpected keyword argument", "cannot import name",
    "expected an indented block", "IndentationError", "SyntaxError",
    "has no attribute", "object is not subscriptable", ...
)
```

素の `KeyError`（`Error: 'results'` だけ）もこちら側です。
`API error: 500` や `Connection timed out` は外部です。

### 2. 「取れなかった」と言う結論に、実際の原因を添える

結論が取得失敗を理由にしていて、失敗の中身がこちらの誤りなら、
**赤い注意書き**を付けます。警告（黄）ではなく、誤りの表示です。

```
❌ この結論の「取得できなかった」は、外部データベースの不在ではなく、
   実行したコードの誤り（5 件）による失敗です。
   データが無いことの根拠にはなりません。実行トレースを確認してください。
```

画面と Markdown レポートの両方に出します。

### 3. そもそも書かせない

```
- 呼び出しが失敗したことは、「データが無い」ことの根拠にならない。
  クエリが失敗したなら「クエリが失敗した」と書くこと。
  「根拠が得られなかった」「データが存在しない」と書いてはいけない。
  まず直すか、別の DB を当たること。
```

## 教訓

**証拠の不在と、不在の証拠は違います。** 道具がその 2 つを混ぜて報告すると、
利用者は「調べた結果、無かった」と読みます。実際には「調べられなかった」
だけです。

§3 で「主張は実行結果に基づかせる」と決めましたが、**否定的な主張にも
同じ基準が要ります**。「無い」と言うにも根拠が要る。
