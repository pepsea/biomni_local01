# 22. context が先に尽きる（タグ無し応答の本当の原因）

§16 では「タグ無し応答」の原因を 3 つ挙げました。実運用で再発したので、
数字で詰め直します。

## 22.1 60 手回すつもりが 5 手で崩れる

`HYPO_MAX_STEPS=60` を既定にしていますが、**context のほうが先に尽きます。**

ReAct の 1 手は think + execute + observation で、observation は biomni が
10K 文字で切ります。1 トークン ≈ 3.5 文字として:

```
1 手あたり ≈ (800 + 600 + 10,000) / 3.5 ≈ 3,300 トークン
```

既定の `num_ctx=32768`、DEFAULT プリセットのシステムプロンプト 16.5k で:

| | 会話に使える | 溢れるまで |
|---|---|---|
| num_ctx=32,768 | 16,268 | **約 5 手** |
| num_ctx=65,536 | 49,036 | 約 15 手 |
| num_ctx=131,072 | 114,572 | 約 35 手 |

**5 手**です。`max_steps=60` は絵に描いた餅でした。

## 22.2 溢れると、真っ先に消えるのがタグの規定

Ollama は num_ctx を超えた分を**古い側から**落とします。会話の先頭にあるのは
システムプロンプトで、**タグの規定はそこにしかありません**。

```
[システムプロンプト: タグの規定]  ← 溢れたら最初に消える
[研究課題]
[think / execute / observation] × N
                                    ← ここで生成する
```

つまり手数が進むほど、規定は「遠ざかる」だけでなく「消える」。
§16 でプロンプト末尾に出力形式を再掲しましたが、**それも会話の先頭側**なので
同じように消えます。対策になっていませんでした。

## 22.3 対処 1: 毎ターン、最後尾に置く

`FormatReminderLLM` が `invoke` のたびに、会話の**最後尾**へ短い念押しを足します。

```
[format] Reply with your reasoning, then EXACTLY ONE tag:
<execute>...python...</execute> to run code, or <solution>...</solution> to finish.
A reply with neither tag is discarded. Never write <observation> yourself.
```

biomni は `self.llm.invoke(messages)` を呼ぶだけなので、`agent.llm` を包めば
**biomni を触らずに**実現できます。

決めたこと:

- **履歴には積まない。** その呼び出しに渡す messages のコピーだけを変えます。
  念押しが履歴に溜まると、それ自体が context を食います
- **メッセージ数を増やさない**（最後が human のとき）。observation は human として
  積まれるので、そこに足すのが自然です
- **最後が assistant のときは、別の human メッセージにする。**
  assistant のメッセージに足すと、モデルは**自分が書いた文章の続き**として
  読みます。指示として効かないどころか、指示文ごと真似されます
- 60 トークン程度。毎ターン払うので短く保ちます

実測（実物の A1 グラフ + モック Ollama、3 ターン）:

```
1 回目: 最後の役割=user  念押し=あり
2 回目: 最後の役割=user  念押し=あり
3 回目: 最後の役割=user  念押し=あり
stop シーケンス: ['</execute>', '</solution>']   ← §4.1 は壊していない
```

## 22.4 対処 2: モデルの上限まで num_ctx を使う

`resolve_num_ctx()` は上限を**超えたときに丸める**だけで、
**下回っているときに上げていませんでした**。

```
qwen3:14b の上限 40,960 / 設定 32,768  → 8,192 を使わず捨てていた
```

上限より小さい値を使う理由がありません。上げます。

```
要求 32,768 / システム 16,500 → num_ctx=40,960  約 7 手
```

## 22.5 対処 3: 手数の限界を、設定した時点で見せる

`estimate_steps_until_full()` を足し、`max_steps` ではなく**実際に回せる手数**を
警告に出します。

> この設定では約 7 手で context が埋まります（残り 24,460 トークン）。
> 埋まると古い側から落ち、タグの規定が消えて「タグ無し応答」になります

## 22.6 それでも足りないとき

| 手 | 効果 | 代償 |
|---|---|---|
| context の大きいモデル | 最も効く（131k で約 35 手） | モデルを替える必要 |
| ツールを `CORE_TOOL_MODULES` に絞る | +2 手程度 | 使えるツールが減る |
| `HYPO_MAX_STEPS` を実態に合わせる | 打ち切りが読める | 探索が浅くなる |
| Claude（1M context） | 事実上上限なし | 質問文が外部に出る |

**`max_steps` を大きくしても手数は伸びません。** context が先に尽きます。
伸ばしたいなら context を増やすか、1 手あたりを軽くするしかありません。

## 22.7 やらないこと

**会話の要約や圧縮**は入れません。observation を要約すると、
そこに含まれる識別子（PMID・アクセッション番号）が落ちます。
§3 の根拠モデルは「実行したコードの出力に識別子が現れたか」で検証するので、
**要約した時点で根拠が検証できなくなります**。
context を節約するために根拠を捨てるのは、このアプリでは本末転倒です。
