# 08. フェーズ計画・受け入れ基準・リスク

## 8.1 フェーズ

各フェーズは「動くものが増える」単位で切る。設計が正しいかを最短で確かめる順序にしてある。

### P0: 足場と検証（最重要・ここで詰まったら設計を見直す）

- Docker Compose（`ollama` / `api` / `worker`）を立て、`qwen3:14b` を pull
- 最小データセット（`gwas_catalog.pkl`, `gene_info.parquet`, `go-plus.json` 程度）だけを取得
- **`agent_factory.build_agent()` を書き、§04 の 4 つの落とし穴を実地で潰す**
  - stop シーケンスが効くか（`<observation>` を自作しないか）
  - `BIOMNI_LLM` / `BIOMNI_SOURCE` で `database.py` が Ollama を使うか
  - データレイク一括ダウンロードが起きないか
  - `num_ctx` を上げてリソース検索が機能するか
- スクリプト 1 本で `question → solution` が通ることを確認

**この時点で「ローカル LLM で Biomni が本当に回るか」が判明する。** 回らないなら
モデルを上げる / `use_tool_retriever=False` に倒す / クラウド LLM を選択肢に戻す、の判断をここで行う。

### P1: 最小 Web ループ

- FastAPI + SSE + SQLite。`POST /runs` → SSE でトレースが流れる → `GET /runs/{id}`
- `TracingRunner` でステップを構造化して永続化
- React で新規ラン画面とトレースタブ
- ラン中断、ワーカークラッシュ時のラン救済

### P2: 根拠層（本アプリの価値）

- `citations.py`（識別子抽出）、`extractor.py`（仮説 JSON 化）、`verifier.py`（実在検証）
- §03.2 の A/B/C 3 段階の集計
- 包含チェック（C ⊆ B）と失敗引用の隔離

### P3: 商用ポリシー層

- `resource_policy.yaml` と 4 重の強制（§05.2）
- ツールレジストリのフィルタ、実行前の静的検査
- ライセンス情報の DB 格納と表示

### P4: UI 完成

- 仮説カード、根拠ドロワー、データタブ、ラン履歴
- Markdown / JSON エクスポート（ライセンスセクション付き）

### P5: 品質と運用

- ユーザーデータアップロード（UC-2）
- 評価セット（§8.3）による回帰テスト
- オフラインモード、外部送信ログ
- モデル別のベンチマーク

## 8.2 受け入れ基準

各フェーズの完了条件。**主観ではなく機械的に判定できる形にする。**

| ID | 基準 | 測り方 |
| --- | --- | --- |
| AC-1 | LLM が `<observation>` を捏造しない | 20 ラン分の生 LLM 出力を検査し、`<observation>` 出現率 0% |
| AC-2 | 外部 LLM API を一切呼ばない | ワーカーコンテナから Ollama 以外への LLM API 通信をネットワークレベルで遮断し、ランが成功する |
| AC-3 | すべての仮説が根拠に紐付く（または未裏付けと明示される） | 仮説 100 件で `evidence == [] && is_supported == true` が 0 件 |
| AC-4 | 引用の捏造が UI に出ない | 検証フェーズで `failed` になった引用が仮説カードに 1 件も表示されない |
| AC-5 | 根拠から実行コードまで 2 クリックで辿れる | 手動 UX チェック |
| AC-6 | 非商用リソースに到達できない | 拒否リストのツール名・データ名を含むコードを注入し、実行前に必ずブロックされる |
| AC-7 | ラン失敗時も途中結果が残る | ワーカーを強制終了させ、それまでのステップが `GET /runs/{id}` で見える |
| AC-8 | レポートにライセンス表記が自動生成される | 使用リソース全件が「使用データとライセンス」表に出る |
| AC-9 | 再現性 | レポートから、同じコードを手で再実行して同じ observation が得られる（外部 DB の更新分を除く） |

## 8.3 評価

「仮説の良さ」は主観だが、**根拠の健全性は測れる**。そこを指標にする。

| 指標 | 定義 | 目標 |
| --- | --- | --- |
| 引用検証率 | verified / (verified + failed) | ≥ 0.95 |
| 根拠付き仮説率 | is_supported な仮説 / 全仮説 | ≥ 0.8 |
| 根拠の平均数 | 仮説あたりの verified な根拠件数 | ≥ 2 |
| トレース完走率 | 成功ラン / 全ラン | ≥ 0.85 |
| 初回イベント遅延 | POST から最初の step イベントまで | ≤ 30 秒 |
| ラン所要時間 | P50 | ≤ 10 分 |

評価用に、**答えが既知の質問 20 件**（教科書的な遺伝子–疾患関係など）を固定セットとして持ち、
モデル変更・プロンプト変更のたびに回す。仮説の正しさは「既知の関係を再発見できるか」で近似する。

## 8.4 リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| **ローカル LLM の指示追従が弱く、A1 のループが成立しない** | 致命的 | P0 で最優先検証。`use_tool_retriever=False` + 固定リソース + 少ないツール数から始める。段階的に増やす |
| ローカル LLM が根拠を捏造する | 本アプリの信頼性の根幹 | §03.4 の機械的検証。「トレースに実在する候補からしか選ばせない」抽出方式 |
| 商用モードでデータが足りず仮説が浅い | 有用性 | §05.1 の代替リソース。除外領域を UI で明示し、期待値を管理する |
| Biomni の API 変更（`_prepare_resources_for_retrieval` 等の非公開メソッドに依存） | 保守性 | 依存箇所を `tracing_runner.py` / `agent_factory.py` に隔離し、Biomni バージョンをピン留め。アップグレード時の契約テストを用意 |
| データレイクのディスク消費 | 運用 | 許可リスト方式で必要分のみ取得。`/datasets` で使用量を可視化 |
| LLM 生成コードによる事故 | 安全性 | §02.6 のコンテナ隔離・タイムアウト・リソース上限 |
| ラン所要時間が長すぎて使われない | 採用 | ステップ上限・ウォールクロック上限、途中結果の即時表示、中断ボタン |
| ライセンス解釈の誤り | 法務 | ポリシーファイルに根拠 URL とレビュー要否を記録。`review_required` は人間の判断を要求する |

## 8.5 実装で最初に書くべき 3 ファイル

設計の妥当性が集中している箇所。ここが書ければ残りは順当に進む。

1. `backend/worker/agent_factory.py` — §04 の落とし穴をすべて封じ込める場所
2. `backend/worker/tracing_runner.py` — A1 の LangGraph を直接回して根拠の原材料を取る場所
3. `backend/worker/verifier.py` — 幻覚引用を落とす場所

この 3 つ以外は、標準的な Web アプリの実装に落ちる。
